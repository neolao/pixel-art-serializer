# Testing

Tests run with Vitest in a jsdom environment (`vitest.config.ts`). Run them with:

```bash
npm run test
```

## What's covered

- **`image-loader.test.ts`** — the file-type check (accepts raster images, rejects non-images and SVG) and the file-reading promise, including its rejection path, by mocking `FileReader`.
- **`upload.test.ts`** — the upload orchestration logic directly (not through DOM events): the nominal path, cancelling the file picker, recovering from a previous error, and rejecting non-image and SVG files.
- **`main.test.ts`** — one end-to-end style test that dispatches a real `change` event on the actual input to confirm the wiring between the page and the upload logic works, on top of the existing test confirming the page mounts its elements.
- **`grid-detection.test.ts`** — `detectPixelGridSize` against synthetic pixel data: a uniform upscaled grid, a grid with non-square cells, a photo-like image with no consistent grid, a tiny image already at native resolution, a grid that's mostly but not perfectly consistent (checks `gridRegularity` lands strictly between 0 and 1), a grid whose cell boundaries are all blurred rather than hard edges, and two invalid-input cases (mismatched pixel data length, zero-sized image) — plus, against real fixture images decoded via `pngjs` (bypassing the canvas dependency below), the exact grid size on four images with a Product-Owner-confirmed expected serialization, and a within-one-cell check on the real bug report that motivated the current algorithm (a pixel-art sprite with soft, anti-aliased edges).
- **`color.test.ts`** — `rgbToLab` / `labDistance`: pins an independently-derived Lab value to confirm two near-black colors are measured as perceptually close, the same way near-white and near-red colors already are (regression coverage for a past bug where dark colors were miscalculated as very far apart).
- **`palette-extraction.test.ts`** — `extractColorPalette` against synthetic pixel data: the reserved transparent color always at index 0 (even for a fully-opaque image), every fully-transparent sample collapsing into that single entry regardless of its underlying RGB, an image with clearly separated opaque colors, near-identical colors that should merge into one palette entry (both a mid-tone and a near-black pair), a merged color normalizing to full opacity when one of its near-identical samples is fully opaque (an anti-aliased source edge), a merged color keeping its partial opacity when none of its near-identical samples is ever fully opaque (an intentionally semi-transparent color), a lone sample's partial opacity preserved as sampled when it has nothing to compare against, a flat single-color image, a pathological case simulating a failed grid detection (thousands of near-random colors, asserting the result still comes back quickly and bounded), and an invalid-input case (mismatched pixel data length).
- **`serializer.test.ts`** — `serializePixelArt` against synthetic pixel data: a grid with clearly separated colors (checks the format version, the grid size, the palette as unified colors, and each pixel's palette index), a flat single-color image, marking only the reserved transparent entry as `reserved`, a case where two near-identical colors are merged and every pixel must still point at the merged entry (not a color no longer in the palette), a fully-transparent pixel that happens to share its RGB with an opaque palette entry (must still map to the reserved transparent index, never to the nearest-color match), an invalid-input case (mismatched pixel data length), and, separately, real `serializePixelArt` output checked with the `ajv` library against the published JSON Schema (`docs/pixel-art-serialization.schema.json`) — both a nominal case and two deliberately malformed documents (the old, superseded shape; a color that isn't an 8-digit hex string) — so the schema can never silently drift from what the code actually produces.
- **`confidence.test.ts`** — `computeConfidence`: a regular grid with a small palette scoring full confidence with a positive verdict, an irregular grid with a large palette scoring none with a negative verdict, a case where the two signals disagree (checks the explanation names which one is weak rather than blending it away), a mid-sized palette scoring proportionally between the two thresholds, and a degenerate zero-color palette still producing a coherent, non-`NaN` result.
- **`palette-editor.test.ts`** — `addPaletteColor`, `removePaletteColor`, `modifyPaletteColor`, `mergePaletteColors`, and `recolorPixel` against a synthetic serialization: adding a color at an index above any existing one (and specifically above any surviving one after a prior removal, not array length), removing a color erasing its pixels to the reserved transparent index while leaving surviving indices uncompacted, refusing to remove or modify the reserved transparent color, modifying a color in place, merging two or three colors into a chosen survivor (checking the survivor keeps its own color rather than a blend, and pixels reassign correctly), merging refusing to act when fewer than two colors are given, when the reserved transparent color is part of the selection, when the survivor isn't part of the selection, or when an unknown index is included, recoloring a pixel to any existing index including the transparent one, and rejecting an unknown palette index or an out-of-range pixel position.
- **`result.test.ts`** — the parts of `result.ts` with no canvas or image-decode dependency: `renderPalette` (one visible swatch per color in index order each showing its hex code, a single-color palette, a transparent color rendered visibly differently from an opaque one, an empty palette hiding the container, the active index highlighted and no other, a color-box click calling `onSelect`, no remove/modify control on the reserved transparent swatch, a remove button / color input calling `onRemove`/`onModify` without also calling `onSelect`, and, in merge-selection mode, checkboxes replacing the modify/remove controls on non-transparent swatches, none on the reserved transparent one, checkbox state reflecting the given selection, a checkbox change calling `onToggleMerge`, a merge-into action appearing only once two or more colors are selected and only on the selected swatches, and normal single-swatch behavior when no selection is given), `resetResult` (hides and clears a previous result including the download link, confidence verdict, and grid size, and is safe to call on an already-empty one), `renderDownloadLink` (the downloadable content matches the current result exactly and the file name is derived from the source image), `toJsonFilename` (replaces an extension, only the last one when there are several, appends one when there is none, and falls back to a default name when no source name is available), `renderConfidence` (formats the verdict, score, and explanation into one sentence, rounding the percentage), and `renderGridSize` (formats the grid's width and height as "W × H pixels", width first, including for a non-square grid and a single-logical-pixel grid).
- **`reconstruction-editor.test.ts`** — `pixelIndexAt` (maps a click near a rect's corners to the right pixel index, and returns `null` outside the rect or for a degenerate zero-size rect), `attachPixelPainter` (calls back with the right index for a click inside the canvas, using a stubbed `getBoundingClientRect`; does nothing for a click outside the canvas or before any serialization is loaded), and `createReconstructionEditor` (renders the palette and download link once loaded; selecting a color then clicking a pixel repaints it, reflected in the downloaded JSON; the canvas is marked in "paint mode" while a color is active and cleared on deselect; removing the active color clears the selection; adding a color appends a swatch; toggling merge mode shows checkboxes instead of modify/remove controls; checking colors and merging into a chosen one shrinks the palette and reassigns pixels, reflected in the downloaded JSON; merging away the currently active paint color switches it to the merge survivor; a color-box click is ignored while merge mode is active; toggling merge mode off before merging leaves everything unchanged; a control used before anything is loaded, or after `reset`, does nothing). The canvas draw itself is stubbed with a minimal fake 2D context (jsdom has none), the same way `getBoundingClientRect` is stubbed — real rendering correctness is still verified only in a real browser, per the gap below.
- **`image-crop.test.ts`** — `cropPixelData` against synthetic position-encoded pixel data (each pixel's channels store its own coordinates, so a crop's correctness is checked against the source directly): a sub-rectangle at a given offset, a crop covering the whole image, a single-pixel crop, fractional rectangle coordinates rounded to the nearest whole pixel, and two invalid-input cases (a rectangle extending beyond the image bounds, a rectangle with no area).
- **`grid-selection.test.ts`** — `resizeFromHandle` (grows/shrinks/shifts the rectangle from each kind of handle, keeps the opposite edge fixed for a side handle, never lets a handle invert the rectangle past its opposite edge, clamps growth at the image bounds), `moveRect` (translates the rectangle, and clamps so it can never be dragged past any edge of the image), and `toImageSpace` (maps a client point through a scaled display rect to natural image coordinates, and returns the origin instead of dividing by zero for a degenerate zero-size display rect).
- **`manual-grid-editor.test.ts`** — `createManualGridEditor` with a stubbed `getBoundingClientRect` on the stage element: `activate` shows the overlay seeded to the whole image with the form pre-filled; dragging a handle (pointerdown/pointermove/pointerup, covering mouse, touch, and pen, including a touch-specific case) resizes the selection and reports the crop only once the drag ends, clamped at the image bounds; dragging the selection body moves it; editing the width/height form reports the new grid size when valid, or shows an inline error and reports nothing for a zero or empty value; keyboard nudging (arrow keys on a handle or the selection body, a bigger step with Shift, unrelated keys ignored); the reset button hides the overlay and notifies the caller; `deactivate` hides the overlay without notifying it.

## What's intentionally not covered by automated tests

A file that has an image MIME type (e.g. `.png`) but is not actually a valid, decodable image is a real case the app handles (it shows an error instead of a broken image icon), but it is **not** covered by an automated test. jsdom's `HTMLImageElement` never fires `load` or `error` for a `data:` URL, so a test that waits for that event would hang, and mocking the event away would only prove the mock works — not the real decode-failure handling. This path was verified manually in a real browser instead. See `.vibe/decisions/001-corrupt-image-verified-at-runtime.md` for the full reasoning.

`pixel-data.ts`'s `extractPixelData` (reads an image's pixels via a canvas) is verified the same way, for the same kind of reason: jsdom has no real 2D canvas, so `getContext("2d")` returns `null` there. It was verified against real sample images in a real browser instead. See `.vibe/decisions/003-canvas-pixel-extraction-verified-at-runtime.md`.

`result.ts`'s `renderReconstruction` (draws the reconstruction to a canvas) and `computeDetection` (the pipeline, triggered by the preview image's `load` event) share both of the gaps above — no real canvas and no real `load` event in jsdom — so they're verified the same way: against real images in a real browser. This covered the full pipeline end to end (a multi-color test image, a single-pixel image, an image with a partially transparent color, the download link's content and file name against a real detection result, a real click on it, a clean synthetic grid scoring 100% confidence, a random-noise photo scoring low with a disagreement explanation, and the error path of selecting an invalid or corrupted file after a result was already shown).

Manual correction was verified the same way, against real images (including one with real transparency) in a real browser: selecting a palette color then clicking a pixel repaints it, verified against the downloaded JSON; erasing a pixel to the reserved transparent color renders it over the checkerboard backdrop; removing, modifying, and adding a palette color all update the swatches, the reconstruction, and the download link; the reserved transparent swatch has no remove/modify controls. This also caught a real bug during development — `renderReconstruction` originally looked up a pixel's color by array position rather than by its stable palette index, which broke as soon as removing a color left a gap — fixed by looking it up by index instead.

Manual merging was verified the same way, against a real multi-color image in a real browser: entering merge mode replaces every non-transparent swatch's modify/remove controls with a checkbox; checking two colors reveals a merge-into action on each; using it shrinks the palette by one, reassigns every pixel of the discarded color to the survivor in the downloaded JSON, and exits merge mode automatically; toggling merge mode off beforehand, without merging, leaves the palette and downloaded JSON unchanged.

The anti-aliased-edge opacity fix was verified the same way, against a real image with a black outline whose grid-aligned edge lands on an anti-aliased source pixel (partial alpha): the reconstruction renders the outline fully solid rather than gray, and the downloaded JSON reports full opacity (255) for that color, while a nominal image with no such edge kept working exactly as before.

`result.ts`'s `computeManualDetection` shares `computeDetection`'s canvas dependency and is verified the same way: against a real image in a real browser, dragging a handle to shrink the selection and confirming the reconstruction, confidence verdict, and grid size all update to reflect only the cropped area; changing the width/height form fields and seeing the grid size update to match; entering an invalid value (zero) and seeing an inline error with the last valid result left in place; nudging a handle with the keyboard (focus + arrow keys, and a bigger step with Shift) and seeing the same live update as a mouse drag, and a touch-originated drag (pointerType "touch") resizing the same way; and "Return to automatic detection" restoring the original result and hiding the manual controls.
