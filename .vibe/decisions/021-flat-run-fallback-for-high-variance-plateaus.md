# Plateau detection falls back to the first sufficiently long run of tied variance values when nothing clears the absolute threshold

**Context:** A Product-Owner-confirmed real image (a hand-drawn 27×29 grid-chart of a pixel-art character, gridlines drawn over shaded, non-flat cell interiors) failed detection entirely (`pixelSize: 1`, i.e. no grid found), even though the manual grid tool confirmed the true grid exists and is clearly visible. `findPlateauEnd` (decisions 018/019) only accepts a candidate cell size whose normalized grid variance drops to or below `PLATEAU_MAX` (0.2) for at least `PLATEAU_MIN_RUN` consecutive candidates. On this image the true cell size (16px) sits on a genuine, wide, stable plateau (7 consecutive candidates producing bit-identical fitted lines) — but its variance value never drops below ~0.486, because every cell has real internal shading, not a single flat color like the project's other fixtures.

**Decision:** When no candidate qualifies against the absolute threshold, fall back to the *first* run of at least `FLAT_RUN_MIN_LEN` (5) consecutive candidates whose normalized variance is bit-identical (within `FLAT_RUN_TOLERANCE`, 1e-9) — skipping the degenerate case where the value sits at the trivial upper bound (~1, meaning no partition was found at all, just the whole image as one box).

**Reason:** The line-fitting DP's ±25% spacing tolerance means nearby candidate cell sizes often converge onto the exact same fitted line set, producing exactly equal grid variance across a run — a plateau signal independent of its absolute level. Picking the *widest* such run (tried first) was wrong: as candidate size grows, the DP has fewer real degrees of freedom, so coincidental ties get longer and longer purely by drifting up the curve, and the widest run in practice was always a coarse, meaningless multiple of the true size, not the true grid. The true grid instead shows up as the *first* run reaching the minimum length, right after the curve's initial choppy rise from the tiny-candidate region. Requiring `FLAT_RUN_MIN_LEN` ≥ 5 (not 2, like `PLATEAU_MIN_RUN`) was necessary because short coincidental ties (length 2-3) occur even on pure noise and on tiny/degenerate images where `fitLines` returns the trivial single-box partition for multiple adjacent candidates.

**Verified for real (not just reasoned):** re-ran the full existing fixture and synthetic test suite (14 cases) plus the new confirmed 27×29 fixture — all pass, including the noisy-image and tiny-native-resolution cases that regressed during a first attempt (picking the widest run, and not excluding the degenerate ~1.0 tie). Also exercised for real in the running app (not just jsdom/pngjs tests): uploading the new fixture through the actual browser upload flow reports the exact confirmed 27×29 grid; re-uploading `pixel-art-cat-sitting.png` and `pixel-art-mario-sprite-blurred-border.png` still reports their previously-confirmed 15×14 and ~15×15 (within the accepted one-cell tolerance) respectively — no visible regression.

**Rejected alternatives:** lowering `PLATEAU_MAX` globally — would need to go well above 0.486 to catch this case, which would then accept far noisier candidates as "plateaus" elsewhere, defeating the threshold's purpose; picking the *widest* flat run anywhere in the curve — rejected per the reason above (latches onto coarse multiples of the true size, and onto the degenerate no-grid tie on trivial/noisy images); requiring exact floating-point equality with no tolerance — kept as-is (1e-9) since the ties observed are genuinely bit-identical (same fitted line arrays), so a wider tolerance was never needed and would only risk false positives.
