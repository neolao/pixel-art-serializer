# Architecture

The app is a small, framework-free TypeScript site built with Vite. Selecting an image both shows an instant preview and, once that preview has decoded, runs the full detection pipeline, hands the result to a reconstruction editor, and displays it next to the original. From there, the user can keep correcting the palette and individual pixels by hand; every edit re-renders the reconstruction and the downloadable JSON.

```mermaid
flowchart LR
    main["main.ts (entry point)"] -->|wires the change event| upload["upload.ts (upload orchestration)"]
    upload -->|reads the file| loader["image-loader.ts (file reading + validation)"]
    upload -->|updates| dom["preview / error DOM elements"]
    main -->|on preview load| computeDetection["result.ts: computeDetection (pipeline)"]
    computeDetection --> pixeldata["pixel-data.ts (canvas pixel extraction)"]
    pixeldata --> griddetect["grid-detection.ts (grid size detection)"]
    griddetect --> palette["palette-extraction.ts (color palette extraction)"]
    palette -->|perceptual color distance| color["color.ts (sRGB to Lab conversion)"]
    griddetect --> serializer["serializer.ts (JSON serialization)"]
    palette --> serializer
    griddetect --> confidence["confidence.ts (pixel-art confidence score)"]
    palette --> confidence
    computeDetection -->|serialization| editor["reconstruction-editor.ts (editor state + rendering)"]
    confidence --> main
    editor -->|renders via| result["result.ts (render functions)"]
    editor -->|pure edit ops| paletteeditor["palette-editor.ts (add/remove/modify/recolor)"]
```

## Modules

**`main.ts`** — Bootstraps the page: renders the upload UI (title, description, file input, preview image, error message, result comparison, palette, add-color controls, download link) into `#app`, and wires the file input's `change` event to `upload.ts`. Resets the input's value after every selection so choosing the same file twice in a row still triggers a change event. Creates one `reconstruction-editor.ts` instance at startup and, on the preview image's `load` event, runs `result.ts`'s `computeDetection` and hands its serialization to the editor's `load` (passing along the selected file's name, used to name the downloadable JSON) plus renders the confidence verdict. Clears the previous result, and resets the editor, synchronously on every new selection, before the new file's outcome is known — so a control used mid-decode can't repaint a stale result.

**`upload.ts`** — Orchestrates one file selection: does nothing if no file was chosen (the picker was cancelled), rejects unsupported types, reads valid images and shows the preview, and shows an error if reading or displaying the image fails. Takes the preview and error elements as plain arguments rather than looking them up itself, which is what makes it testable without spinning up the whole page.

**`image-loader.ts`** — Two pure functions with no DOM dependency: `isSupportedImageType` (rejects non-images and SVG, since the grid/palette detection features built later need raster pixel data) and `readImageFile` (wraps `FileReader` in a promise that resolves with a data URL or rejects on read failure).

**`grid-detection.ts`** — Pure function `detectPixelGridSize`: scans up to 24 full rows and 24 full columns of an image's pixel data, pools same-color segment lengths per axis, and takes the most frequent length as the logical pixel size. Returns the detected pixel size plus the image's width/height expressed in logical pixels rather than raw pixels, plus a `gridRegularity` score (0-1): the share of scanned runs that actually match that size, forced to 0 whenever no consistent size was found at all (`pixelSize` of 1). No DOM dependency, so it's tested with synthetic pixel data.

**`pixel-data.ts`** — `extractPixelData`: reads a loaded `<img>`'s real pixel data via an offscreen canvas (`drawImage` + `getImageData`), at the image's natural resolution. Not covered by automated tests — see [docs/testing.md](testing.md).

**`palette-extraction.ts`** — Pure function `extractColorPalette`: given the raw pixel data and a detected grid, samples one raw pixel per logical grid cell (the one nearest the cell's center), then repeatedly merges the two perceptually closest colors (in Lab space, via `color.ts`) while they stay under a "just noticeable difference" threshold, so near-identical colors caused by compression artifacts collapse into one palette entry. The first entry is always a reserved fully-transparent color (index 0), even when the source image has no transparency at all; every fully-transparent raw sample collapses into that single entry regardless of its underlying RGB — see `.vibe/decisions/011-palette-always-reserves-transparent-index-zero.md`. Returns the indexed list of distinct colors plus their count. Guards against pathological input (e.g. grid detection finding no grid on a large, noisy image) by coarsely bucketing colors first whenever there would otherwise be too many to merge pairwise in reasonable time.

**`color.ts`** — Three pure functions with no dependency on the rest of the app: `rgbToLab` (sRGB to CIE Lab conversion), `labDistance` (CIE76 perceptual distance between two Lab colors), and `rgbToHex` (channel values to a `#rrggbb` string), used by `palette-extraction.ts` and `serializer.ts`.

**`serializer.ts`** — Pure function `serializePixelArt`: given the raw pixel data, the detected grid, and the extracted palette, resamples each grid cell's color (the same way `palette-extraction.ts` samples it) and assigns it to the closest palette entry in Lab space, so a pixel whose original shade was folded into another during palette extraction still ends up pointing at the entry that absorbed it. A fully-transparent sample always maps to the reserved transparent entry (index 0) directly, never by Lab distance, so a fully-opaque color that happens to share its RGB (e.g. black) can never be mistaken for it. Returns one JSON-ready object: grid width/height, the palette as `{ index, hex, alpha }` entries, and a flat, row-major array of one palette index per logical pixel.

**`confidence.ts`** — Pure function `computeConfidence`: averages two 0-1 signals — the detected grid's `gridRegularity` and a palette-size score (1 at 16 colors or fewer, 0 at 256 or more, sliding linearly in between, since pixel art conventionally uses a small, fixed palette) — into an overall score, a plain-word verdict ("Looks like pixel art" / "Doesn't look like pixel art" at the 50% mark), and a one-clause explanation naming which of the two signals is weak when they disagree, or both/neither when they agree. See `.vibe/decisions/009-grid-regularity-exposed-from-detection.md` for why grid regularity is computed inside grid detection rather than here.

**`result.ts`** — The pipeline and the render primitives. `computeDetection` runs `pixel-data.ts` → `grid-detection.ts` → `palette-extraction.ts` → `serializer.ts` / `confidence.ts` and returns the grid, palette, and serialization, without touching the DOM. `resetResult` hides the reconstruction, palette, download link, and confidence verdict, and clears any previous swatches, downloadable content, and verdict text (called on every new file selection, before that file's outcome is known, so nothing stale ever lingers). `renderPalette` builds one labeled, interactive color swatch per palette entry, in index order: each shows its hex code and its color over a checkerboard backdrop (so a transparent color reads as transparent), a click on the color box selects it as the active color via `onSelect`, and every entry except the reserved transparent one also gets a color-picker input (`onModify`) and a remove button (`onModify`/`onRemove`) — the active entry gets a visible highlight. `renderReconstruction` draws the reconstruction straight onto a `<canvas>` sized to exactly the grid's width and height (one canvas pixel per logical pixel, styled with `image-rendering: pixelated` and the grid's own aspect ratio), looking up each pixel's color by its palette `index` (not its array position, since manual removal can leave gaps) and reading colors only from the serialized JSON so it can never be influenced by the original image's actual pixels — see `.vibe/decisions/007-reconstruction-rendered-to-live-canvas.md`. `renderDownloadLink` sets the download link's `href` to a `data:application/json` URL holding the exact serialized JSON, and its filename via `toJsonFilename` (the source file's name with its extension replaced by `.json`, or a fixed fallback name when none is available) — see `.vibe/decisions/008-json-download-via-data-url.md`. `renderConfidence` writes the verdict, its score as a rounded percentage, and the explanation as one sentence into a `role="status"` element, so assistive tech announces it the same way the rest of a newly-produced result appears. `resetResult`, `renderPalette`, `renderDownloadLink`, `toJsonFilename`, and `renderConfidence` are covered by automated tests; `renderReconstruction`/`computeDetection` are not, for the same reason as `pixel-data.ts` — see [docs/testing.md](testing.md).

**`palette-editor.ts`** — Five pure functions with no DOM dependency, each returning a new `PixelArtSerialization` rather than mutating the input: `addPaletteColor` (appends a color at `max(existing indices) + 1`, never at array length, so it can never collide with an index a prior removal left behind), `removePaletteColor` (erases every pixel pointing at the removed color to the reserved transparent index 0 — distinct from the automatic reduction and manual merge features, which reassign to the nearest perceptually-similar color instead; surviving entries keep their original index, uncompacted), `modifyPaletteColor` (changes a color's value in place, so every pixel already pointing at it updates for free), `mergePaletteColors` (given two or more selected indices and a survivor among them, reassigns every pixel pointing at a non-survivor to the survivor and drops the non-survivor entries, keeping the survivor's own color rather than computing a blend; a no-op if fewer than two colors are given, the survivor isn't part of the selection, an unknown index is included, or the reserved transparent color is part of the selection), and `recolorPixel` (reassigns one pixel to any existing palette index, including the transparent one). The reserved transparent color at index 0 can never be removed, modified, merged, or targeted by these guards being bypassed — see `.vibe/decisions/011-palette-always-reserves-transparent-index-zero.md`, `.vibe/decisions/012-remove-palette-color-erases-to-transparent.md`, and `.vibe/decisions/013-palette-merge-as-distinct-selection-mode.md`.

**`reconstruction-editor.ts`** — Wires manual editing to the screen. `pixelIndexAt` is a pure function mapping a click's viewport coordinates to a logical-pixel index, accounting for the canvas being drawn at one unit per logical pixel but displayed scaled up via CSS. `attachPixelPainter` attaches a canvas click listener that calls it and reports the resulting pixel position. `createReconstructionEditor` holds the current serialization, the active color index, and the merge-selection state for one result: `load` installs a freshly-detected serialization and re-renders; `reset` clears it so a control used while a new image is still decoding can't silently repaint the previous result; internally, selecting a swatch, removing or modifying a color, adding one, or clicking a pixel with a color active all go through `palette-editor.ts` and re-render via `result.ts`'s render functions. A dedicated merge-mode toggle switches the palette into a checkbox-based multi-select for `mergePaletteColors`: while active, a swatch's normal color-box click (paint selection) is disabled to keep the two interactions unambiguous, but any paint color already active before entering merge mode is preserved and automatically follows the merge survivor if it gets merged away, rather than being cleared — see `.vibe/decisions/013-palette-merge-as-distinct-selection-mode.md`. Attached once at startup to the persistent canvas, "add color" button, and merge-toggle button (rather than re-attached on every new image) to avoid stacking duplicate listeners across uploads.

## Data flow

**Upload/preview (live):**
1. The user picks a file in the `#image-input` field.
2. `main.ts`'s change handler calls `resetResult` immediately, then reads `input.files[0]` and calls `upload.ts`.
3. `upload.ts` validates the type via `image-loader.ts`; on success it reads the file (also via `image-loader.ts`) and sets the preview image's `src` to the resulting data URL; on failure it shows an inline error and hides the preview.
4. If the file passed the type check but isn't actually a valid image (a corrupted file), the preview `<img>`'s own `onerror` handler catches the browser's decode failure and swaps back to the error message. Either way, the result section stays hidden — `displayResult` only ever runs after a successful decode.

**Grid detection, palette extraction, JSON serialization, and result display (live):** once the preview `<img>` fires its `load` event (a successful decode), `main.ts` calls `result.ts`'s `computeDetection`, which reads the image's raw pixels via canvas (`pixel-data.ts`), detects its logical pixel grid (`grid-detection.ts`), extracts its color palette (`palette-extraction.ts`), and serializes both into JSON (`serializer.ts`) and into a confidence verdict (`confidence.ts`). `main.ts` hands the resulting serialization to the reconstruction editor (`reconstruction-editor.ts`), which renders the reconstruction, the palette swatches, and the JSON download link, and renders the confidence verdict itself.

**Manual correction (live):** selecting a palette swatch's color box makes it the active color; clicking a pixel in the reconstruction repaints it with the active color, via `palette-editor.ts`'s `recolorPixel`. Adding, removing, or changing a palette color goes through the same module's `addPaletteColor` / `removePaletteColor` / `modifyPaletteColor`. Toggling merge mode switches the palette to checkboxes; checking two or more colors and picking one to merge into calls `mergePaletteColors`, then exits merge mode automatically. Every one of these edits re-renders the reconstruction, the palette, and the download link immediately, so the exported JSON always matches what's on screen.
