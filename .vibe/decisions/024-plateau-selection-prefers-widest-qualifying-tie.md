# Grid-size plateau selection prefers the widest bit-identical tie under a value cap, not the last or lowest-valued candidate

**Context:** A Product-Owner-confirmed real image (a 255×255 owl sprite, native-resolution export with a one-logical-pixel-wide fully-transparent left margin) was detected as a 4×4 grid instead of the confirmed 15×15. `findPlateauEnd`'s absolute-threshold scan (decisions 018/019) returns the *last* candidate cell size whose normalized grid variance clears `PLATEAU_MAX` (0.2) within a run — but on this image, nothing between the true plateau (candidates 14-22, normalized variance ~1.19e-7, an almost-perfect fit) and a much coarser, merely-adequate region (candidates 23-52, variance 0.13-0.23) ever exceeds 0.2, so the scan walks straight past the true plateau into the coarse one.

**Decision:** Try a new check, `findFloorRunEnd`, before the existing absolute-threshold scan: group the candidate sweep into maximal runs of bit-identical values (the line-fitting DP converging on the exact same fitted lines — the same signal `findFlatRunEnd`, decision 021, already trusts), keep only runs whose length reaches both `FLAT_RUN_MIN_LEN` (5) and `FLOOR_RUN_MIN_WIDTH_RATIO` (0.3) of their own end candidate value, and among those pick the **widest** one (ties broken by lowest value) rather than the lowest-valued one outright. Falls through to the original absolute-threshold scan, then to `findFlatRunEnd`, when nothing qualifies.

**Reason:** Three properties, each independently falsified by a real fixture during development, had to hold at once:
1. *Not last-under-a-fixed-cap* — the owl case above.
2. *Not simply lowest-tied-value* — on a real cat photo, a coincidental 5-long tie at candidate 24 (variance 0.073) out-scored the genuine 19-long tie spanning candidate 50 (variance 0.092, containing the confirmed ~40px cell size), purely by having a marginally lower number; picking by value alone regressed a previously-passing fixture.
3. *Not simply widest-tied-value* — on a real Mario sprite, a 52-long tie at candidate ~155 (variance 0.57 — a worse fit than three-quarters of the whole image's own color spread) out-scored the genuine 25-long tie spanning candidate 50 (variance 0.047, containing the confirmed ~42px size); very large candidates can tie over a wide range simply because the line-fitting DP has few real degrees of freedom left at that scale, not because they represent real structure.
`FLOOR_RUN_MIN_WIDTH_RATIO` (0.3) is derived from `LINE_TOLERANCE` (±25%): a genuine plateau's width scales with its own candidate value (candidates within the tolerance band of a true cell size all converge to the same lines), so requiring the run's length to reach a meaningful share of its own scale rejects small-scale coincidental ties without an arbitrary absolute cutoff. Combining it with the pre-existing `PLATEAU_MAX` cap rejects wide-but-poor-fit ties at very coarse scales. Together, width (among qualifying candidates) breaks ties between two genuine plateaus at different real scales (e.g. a sprite's overall grid vs. a smaller repeating internal detail), consistent with decision 019/021's existing width-as-trust-signal reasoning.

**Verified for real (not just reasoned):** re-ran the full grid-detection test suite (all real fixtures with Product-Owner-confirmed sizes, all synthetic cases) — 15/15 pass, including the four fixtures used to derive each of the three properties above, with no regression. Confirmed in a real browser: uploading the owl fixture now reports the confirmed 15×15 grid.

**Rejected alternatives:** anchoring `findFlatRunEnd`'s existing pairwise (previous-candidate) comparison instead of adding a dedicated check — rejected because a chain of small pairwise steps in the tiny-candidate over-partitioned region can drift past any reasonable tolerance without any single step tripping it, producing the same false-plateau problem one level down. Picking by lowest tied value alone, or widest tied run alone — both rejected per point 2 and 3 above, each independently regressing a different real fixture.
